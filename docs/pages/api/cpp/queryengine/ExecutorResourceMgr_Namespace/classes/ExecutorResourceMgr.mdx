`ExecutorResourceMgr` is the central manager for resources available to all executors in the system.

It manages an [`ExecutorResourcePool`](executorresourcepool) to keep track of available and allocated resources (currently CPU slots/threads, GPUs, CPU result memory, and CPU and GPU buffer pool memory). It also manages a thread queue which keeps requesting threads (from `Executor::launchKernelsViaResourceMgr`) waiting until there it can schedule them. At that point, it gives the calling executor thread a `ResourceHandle` detailing the resources granted to the query, which once it goes out of scope will return the granted resources to the [ExecutorResourcePool](executorresourcepool).

### pause_process_queue [#pauseprocessqueue]

<CodeBlock links={{"ExecutorResourceMgr": "executorresourcemgr"}}>
```cpp showLineNumbers={false}
void ExecutorResourceMgr_Namespace::ExecutorResourceMgr::pause_process_queue()
```
</CodeBlock>

Pauses the process queue in a thread-safe manner, waiting for all queries in the executing stage to finish before yielding to the caller (ensuring that the [ExecutorResourcePool](executorresourcepool) has no outstanding allocations).

If the process queue is already paused, the call is a no-op. This method is used to live-change parameters associated with [ExecutorResourcePool](executorresourcepool).

Note that when the queue is fully paused, there will be no executing requests but there can be one or more queued requests.

### choose_next_request [#choosenextrequest]

<CodeBlock links={{"ExecutorResourceMgr": "executorresourcemgr"}}>
```cpp showLineNumbers={false}
RequestId ExecutorResourceMgr_Namespace::ExecutorResourceMgr::choose_next_request()
```
</CodeBlock>

Internal method: Invoked from `process_queue_loop`, chooses the next resource request to grant.

Currently based on FIFO logic, choosing the oldest request in the queue that we have enough resources in [`ExecutorResourcePool`](executorresourcepool) to fulfill. Future variants could add more sophisticated logic for more optimal query scheduling (i.e. non-FIFO).

**Returns:** [RequestId](../typedefs/requestid) - The id of the request we will grant resources for.

### enqueue_request [#enqueuerequest]

<CodeBlock links={{"ExecutorResourceMgr": "executorresourcemgr", "RequestInfo": "../structs/requestinfo", "ResourceGrant": "../structs/resourcegrant"}}>
```cpp showLineNumbers={false}
RequestId ExecutorResourceMgr_Namespace::ExecutorResourceMgr::enqueue_request(
    const RequestInfo &request_info,
    const size_t timeout_in_ms,
    const ResourceGrant &min_resource_grant,
    const ResourceGrant &max_resource_grant
)
```
</CodeBlock>

Internal method: Invoked from request_resource/request_resource_with_timeout, places request in the request queue where it will be wait to be granted the resources requested.

Note that this method assigns a [`RequestId`](../typedefs/requestid) to the request, adds the request to the [`RequestStats`](../structs/requeststats), and adds the assigned request_id to the QUEUED stage, but does not actually notify the process queue or queue the request in the `OutstandQueueRequests` object. Those tasks are done subsequently to invocation of this method in the parent call ([`request_resources_with_timeout`](#requestresourceswithtimeout))

**Returns:** [RequestId](../typedefs/requestid) - generated request id for this request

**Parameters**

<ParamField path="request_info" type="const RequestInfo &">
- Info for the current resource request
</ParamField>

<ParamField path="timeout_in_ms" type="const size_t">
- Request timeout
</ParamField>

<ParamField path="min_resource_grant" type="const ResourceGrant &">
- Min allowable resource request, calculated in caller [`request_resources_with_timeout`](#requestresourceswithtimeout) method from request_info
</ParamField>

<ParamField path="max_resource_grant" type="const ResourceGrant &">
- Max (ideal) resource request, calculated in caller [`request_resources_with_timeout`](#requestresourceswithtimeout) method from request_info
</ParamField>
